# 前端技术方案（配置中心管理界面）

> 项目：k_config_center（ASP.NET Core Web API + SqlSugar + PostgreSQL）
> 配套文档：`docs/设计文档/配置中心设计文档.md` | `docs/数据库脚本/配置中心建表脚本.sql`

---

## 1. 背景与目标

k_config_center 目前是一个纯后端的 ASP.NET Core Web API 项目，配置数据的层级模型（命名空间 → 环境 → 配置组 → 配置项 → 版本快照）与发布/回滚机制均已在设计文档中定稿。为了让配置的日常维护脱离直接操作数据库或裸调 API，需要为配置中心增加**管理界面（Portal）**能力。

核心页面诉求：

- **命名空间 / 环境 / 配置组管理**：基础三级维度的增删改查与启用/禁用；
- **配置编辑**：支持多格式内容（text / json / yaml / properties / xml / toml）的编辑，并具备对应的语法高亮与基础校验；
- **版本历史与 Diff 对比**：查看某配置项的全部历史版本快照，任意两个版本（或当前编辑态与已发布版本）之间的差异对比；
- **发布 / 回滚**：将草稿内容发布为新版本，或以历史版本内容生成新版本回滚，配合「有未发布变更」标记；
- **操作审计**：按命名空间 / 环境 / 配置项等维度检索操作日志（config_center_operation_log）。

## 2. 候选方案对比

| 方案 | 技术组合 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| 方案一 | 前后端分离 SPA：Vue 3 + Element Plus | 生态成熟、中文资料丰富、组件覆盖全面；模板语法上手门槛低 | 需要引入 Node 工具链；中后台高阶封装（如 ProTable 一类）不如 React 生态完整 | 团队以 Vue 技术栈为主、追求快速上手的中后台项目 |
| 方案二 | 前后端分离 SPA：React 18 + Ant Design 5 | 生态同样成熟；AntD ProComponents（ProTable/ProForm）对 CRUD 类中后台页面提效明显；TypeScript 支持一流；Monaco、Diff 等编辑器周边组件最丰富 | 需要引入 Node 工具链；JSX 心智模型对纯后端团队略有门槛 | 中后台管理系统的主流选择，页面以表格 + 表单 + 编辑器为主的场景 |
| 方案三 | Blazor（Server 模式 + MudBlazor） | 纯 C# 技术栈，.NET 团队零前端成本上手最快；与后端共用模型类型 | 组件生态明显弱于 Vue/React；富文本/代码编辑器等复杂组件多依赖 JS 互操作；Server 模式依赖常连接，弱网体验差 | 全员 .NET、界面复杂度中低、不想维护双技术栈的团队 |
| 方案四 | Razor Pages + htmx 轻量方案 | 架构最简单，无独立前端工程，部署零额外成本 | 富交互页面（代码编辑器、版本 Diff、多面板联动）实现吃力，可维护性随交互复杂度快速恶化 | 页面以静态展示 + 简单表单为主的小型工具站 |

**结论：选定方案二 —— React 18 + TypeScript + Ant Design 5。**

理由：配置中心 Portal 的核心页面高度依赖「表格 + 表单 + 代码编辑器 + Diff 视图」，React 生态在这几类组件上的成熟度与可组合性最好（@monaco-editor/react、react-diff-viewer-continued 均为开箱即用）；ProComponents 可显著压缩命名空间/环境/配置组等 CRUD 页面的开发量。

## 3. 选定方案技术栈清单

| 类别 | 选型 | 说明 |
|------|------|------|
| 构建工具 | Vite | 开发启动快、配置简单，内置 dev 代理能力 |
| 语言 | TypeScript | 与后端 Response/Request 模型对齐，减少接口联调错误 |
| UI 组件库 | Ant Design 5 | 中后台组件覆盖全面 |
| 路由 | react-router v6 | 声明式路由，配合布局组件实现侧边栏导航 |
| 状态管理 | Zustand | 轻量，仅用于全局共享的少量状态（当前命名空间/环境上下文等） |
| HTTP 客户端 | Axios（可选 TanStack Query） | Axios 拦截器统一处理错误提示与响应解包；数据缓存/重试等诉求增强时可引入 TanStack Query |
| 代码编辑器 | @monaco-editor/react | VS Code 同源内核，原生支持 json/yaml/xml 等语法高亮 |
| 版本对比 | react-diff-viewer-continued | 双栏/单栏 Diff 视图，用于版本历史对比 |
| 中后台增效（可选） | AntD ProComponents | ProTable / ProForm 提效命名空间、环境、配置组等 CRUD 页面 |

## 4. 工程目录规划

### 4.1 仓库根目录

```
k_config_center/                        （仓库根）
├── k_config_center.sln                  # 解决方案文件（仅包含后端项目）
├── docs/                                # 项目文档（设计文档 / 数据库脚本 / 技术方案）
├── k_config_center/                     # 后端：ASP.NET Core Web API
└── web/                                 # 前端：React SPA（不加入 .sln）
```

- `web/` 作为独立前端工程放在仓库根，**不加入 .sln**：.NET 工具链不感知前端工程，前端由 Node 工具链独立管理，二者仅通过构建产物目录（wwwroot）与 API 契约耦合。

### 4.2 后端 k_config_center/ 目录

```
k_config_center/
├── Program.cs                                    # 入口：服务注册、SqlSugar 接入、静态文件与兜底路由
├── Controllers/                                  # API 控制器（统一 /api 前缀）
│   ├── NamespaceController.cs                    # 命名空间管理
│   ├── EnvironmentController.cs                  # 环境管理
│   ├── ConfigurationGroupController.cs           # 配置组管理
│   ├── ConfigurationController.cs                # 配置项管理：编辑、发布、回滚、版本历史
│   └── ClientConfigurationController.cs          # 面向客户端 SDK：配置读取与长轮询变更探测
├── Entities/                                     # SqlSugar 实体（对应 6 张表，映射规则见设计文档第 6 章）
│   ├── ConfigCenterNamespace.cs
│   ├── ConfigCenterEnvironment.cs
│   ├── ConfigCenterConfigurationGroup.cs
│   ├── ConfigCenterConfiguration.cs
│   ├── ConfigCenterConfigurationVersion.cs
│   └── ConfigCenterOperationLog.cs
├── Models/                                       # 接口出入参模型（与实体隔离）
│   ├── Requests/                                 # 请求模型（创建/更新/发布/回滚等）
│   └── Responses/                                # 响应模型（列表项/详情/版本对比等）
├── Services/                                     # 业务逻辑层
│   ├── NamespaceService.cs                       # 命名空间/环境/配置组等基础维度的业务逻辑
│   ├── ConfigurationService.cs                   # 配置编辑：内容保存、md5 计算、未发布变更判断
│   └── PublishService.cs                         # 发布/回滚：事务内写版本快照、更新生效版本指针
├── Infrastructure/                               # 基础设施
│   ├── SqlSugarSetup.cs                          # SqlSugar 客户端注册（PostgreSQL 连接、实体特性解析）
│   └── OperationLogFilter.cs                     # 审计切面：拦截写操作并落 config_center_operation_log
└── wwwroot/                                      # 前端构建产物输出目标（加入 .gitignore，不提交）
```

- **Controllers**：管理端接口（Namespace/Environment/ConfigurationGroup/Configuration）与客户端读取接口（ClientConfiguration）分开，读写职责清晰，对标 Apollo 的 AdminService / ConfigService 分离演进方向；
- **Entities 与 Models 分离**：实体只承担 ORM 映射，接口出入参用独立的 Requests/Responses 模型，避免数据库结构直接暴露；
- **Services**：发布/回滚涉及「版本号自增 + 写快照 + 更新指针 + 写审计」的事务操作，集中在 PublishService，避免散落在控制器；
- **Infrastructure/OperationLogFilter**：以过滤器（切面）方式统一记录操作审计，业务代码不必逐处手写日志。

    │   ├── environment/
    │   │   └── EnvironmentList.tsx       # 环境列表与增删改
    │   ├── group/
    │   │   └── GroupList.tsx             # 配置组列表与增删改
    │   ├── configuration/
    │   │   ├── ConfigurationList.tsx     # 配置项列表：状态/未发布变更标记、发布/下线入口

    │   │   └── VersionHistory.tsx        # 版本历史：版本列表 + Diff 对比 + 回滚入口
    │   └── audit/
    │       └── OperationLogList.tsx      # 操作审计：多维度检索操作日志

- **api/ 分层**：所有请求经由 `http.ts` 的 Axios 实例，拦截器统一弹出错误提示并解包响应体，页面代码只关心业务数据；`types.ts` 与后端 Models 保持字段一致；
- **store/useScopeStore.ts**：命名空间与环境是几乎所有页面的过滤上下文，用 Zustand 全局持有，顶栏切换后各列表页联动刷新；
- **pages 按资源分目录**：与后端 Controllers 一一对应，便于前后端对照维护。

## 5. 开发与部署机制

### 5.1 开发阶段

- 后端 `dotnet run`（默认监听本地端口）与前端 `npm run dev` 并行启动；
- `vite.config.ts` 中将 `/api` 前缀的请求代理到后端地址，浏览器侧同源访问，**无跨域问题**，后端无需配置 CORS；
- 前端热更新与后端热重载互不干扰，联调只依赖 API 契约。

### 5.2 部署阶段

- `npm run build` 将产物输出到 `../k_config_center/wwwroot`（由 `build.outDir` 指定）；
- 后端启用 `UseStaticFiles()` 托管静态资源，并以 `MapFallbackToFile("index.html")` 兜底前端路由（浏览器直接访问 `/configuration/list` 等前端路由时回落到 index.html，由 react-router 接管）；
- 最终形态为**单一应用部署**：一个 ASP.NET Core 进程同时提供 API 与静态页面，运维成本最低；
- 保留将来前端独立部署到 Nginx 的可能：前端工程本身与后端无构建耦合，届时仅需调整 `build.outDir` 与 API 基地址，并在后端补充 CORS 配置。

### 5.3 工程约定

| 约定 | 说明 |
|------|------|
| `web/` 不进 .sln | 前端由 Node 工具链独立管理，.NET 解决方案保持纯后端 |
| `wwwroot/` 进 .gitignore | 构建产物不入库，由 CI/发布流程按需生成 |
| API 统一 `/api` 前缀 | 便于 dev 代理与部署时静态资源/接口路由区分 |
| 管理端与客户端接口分控制器 | 管理接口（增删改/发布/回滚）与客户端读取接口（拉取/长轮询）职责分离，对标 Apollo 的 AdminService / ConfigService 分离演进方向 |
