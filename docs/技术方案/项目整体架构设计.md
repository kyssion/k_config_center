## 1. 项目背景与目标

k_config_center 是一个自研配置中心，用于集中管理应用配置，替代散落在各应用中的配置文件与手工改库操作。核心能力：

- **层级隔离模型**：namespace（命名空间）→ environment（环境）→ configuration_group（配置组）→ configuration（配置项），支持多业务线、多环境隔离；
- **版本与快照**：配置每次发布产生不可变的历史版本快照，版本号线性递增；
- **状态机**：配置具备 DRAFT / PUBLISHED / OFFLINE 状态流转与软删除能力；
- **发布 / 回滚**：草稿发布为新版本；回滚以历史版本内容生成新版本，历史可追溯；
- **操作审计**：所有写操作（创建 / 修改 / 发布 / 回滚 / 下线 / 删除）落审计日志；
- **客户端读取**：面向应用客户端提供已发布配置的读取与长轮询变更探测接口。

## 5. 开发与部署机制

### 5.1 开发阶段（双进程）

- 后端 `dotnet run` 与前端 `npm run dev` 并行启动；
- Vite 开发服务器将 `/api` 前缀请求代理到后端地址，浏览器侧同源访问，无跨域问题，后端无需配置 CORS；
- 前端热更新与后端热重载互不干扰，联调只依赖 API 契约。

### 5.2 部署阶段（单一应用）

- `npm run build` 将前端产物输出到 `k_config_center/wwwroot/`；
- 后端启用 `UseStaticFiles()` 托管静态资源，并以 `MapFallbackToFile("index.html")` 兜底前端路由（浏览器直接访问前端路由地址时回落到 index.html，由 react-router 接管）；管道顺序上，`UseStaticFiles()` 注册在 `UseHttpsRedirection()` 之后，`MapFallbackToFile("index.html")` 注册在 `MapControllers()` 之后，保证 API 路由优先于兜底命中；`/api` 前缀不参与 SPA 兜底（通过更高优先级的 `MapFallback("/api/{*path}")` 兜底端点实现），未知 API 路径直接返回 404，避免客户端/SDK 把 index.html 当成功响应解析；
- 最终形态为**单一应用部署**：一个 ASP.NET Core 进程同时提供 API 与静态页面，运维成本最低；
- 保留将来前端独立部署到 Nginx 的可能：届时仅需调整构建输出目录与 API 基地址，并在后端补充 CORS 配置。

### 5.3 工程约定

| 约定 | 说明 |
|------|------|
| `web/` 不进 .sln | 前端由 Node 工具链独立管理，.NET 解决方案保持纯后端 |
| `wwwroot/` 进 .gitignore | 构建产物不入库，由 CI / 发布流程按需生成 |

## 6. 接口分层约定

- 所有接口统一 **`/api` 前缀**，便于开发代理与部署时静态资源 / 接口路由区分；
- **管理端接口与客户端读取接口分控制器**：
  - 管理端接口：命名空间 / 环境 / 配置组 / 配置项的增删改、发布、回滚、版本历史、审计查询，服务于 Portal；
  - 客户端接口：已发布配置的读取与长轮询变更探测，服务于应用客户端（未来 SDK）；
- 读写职责分离，对标 Apollo 的 AdminService / ConfigService 拆分：当前同进程内以控制器边界隔离，未来可平滑拆分为独立服务；
- 具体端点定义、统一响应结构与错误码约定见 `./后端方案.md`。

## 7. 演进路线

| 阶段 | 范围 | 说明 |
|------|------|------|
| 阶段一（当前） | 管理 Portal + 管理端 API + 客户端读取/长轮询 API | 单进程部署，覆盖配置管理全流程（编辑、发布、回滚、审计） |
| 阶段二 | 组级发布快照 / ReleaseMessage / 灰度发布 | 引入组级发布与变更消息机制提升长轮询效率；灰度规则按 IP / 标签 / 百分比命中灰度版本 |
| 阶段三 | 客户端 SDK 与服务拆分 | 提供 .NET 客户端 SDK（本地缓存 + 长轮询热更新）；管理端与客户端接口拆分为独立服务独立伸缩 |
