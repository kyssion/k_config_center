# 后端方案（配置中心服务端）

> 定位：纯后端视角的技术方案。
> 配套文档：`./项目整体架构设计.md`（顶层架构与部署）| `./前端方案.md`（Portal 前端）| `../设计文档/配置中心设计文档.md`（领域模型与机制设计）| `../数据库脚本/配置中心建表脚本.sql`（DDL）

---

## 1. 背景与职责

后端为配置中心提供全部服务端能力，职责边界：

- **管理端 API**：命名空间 / 环境 / 配置组 / 配置项的增删改查，服务于管理 Portal；
- **客户端 API**：已发布配置的读取与长轮询变更探测，服务于应用客户端（未来 SDK）；
- **发布 / 回滚领域逻辑**：版本号递增、不可变快照写入、生效版本指针切换的事务实现；
- **操作审计**：所有写操作统一落 `config_center_operation_log`；
- **静态资源托管**：`wwwroot/` 托管前端构建产物并兜底前端路由（参见 `./项目整体架构设计.md`）。

## 2. 技术栈

| 类别 | 选型 | 说明 |
|------|------|------|
| Web 框架 | ASP.NET Core Web API | 控制器风格，统一 `/api` 前缀 |
| ORM | SqlSugar（NuGet：SqlSugarCore） | `DbType.PostgreSQL`，实体仅做映射，禁用 CodeFirst 建表（见第 5 章） |
| 数据库 | PostgreSQL 14+ | DDL 由建表脚本手工执行 |
| API 文档（可选） | Swashbuckle 或 Scalar | 开发期生成 OpenAPI 文档与调试界面 |

各层职责：

- **Controllers**：管理端接口（Namespace / Environment / ConfigurationGroup / Configuration）与客户端读取接口（ClientConfiguration）分开，读写职责清晰，对标 Apollo 的 AdminService / ConfigService 分离演进方向；
- **Entities 与 Models 分离**：实体只承担 ORM 映射且只在 Repositories 层出现；Service 层用 Models/Domain 业务数据类处理业务，接口出入参用独立的 Requests / Responses 模型，避免数据库结构直接暴露；
- **Services 按模块拆分**：一个 Service 只管一种资源，模块边界清晰；发布/回滚涉及「版本号自增 + 写快照 + 更新指针 + 写审计」的事务操作，集中在 PublishService，避免散落在控制器；
- **Repositories 按模块拆分**：数据库的查询/写入（Queryable / Insertable / Updateable / 原生 SQL）全部收口到各模块的 Repository，实体 ↔ 业务数据的映射（静态 From/To 方法）也写在 Repository 内；
- **审计日志**：各业务 Service 在操作成功后调 OperationLogRepository 写 config_center_operation_log，事务型操作（发布/回滚）的日志在事务内写入。

## 4. 分层设计

```
HTTP 请求
   │
   ▼
Controller（Controllers/）
   ├─ 参数绑定与模型校验（Requests 模型）
   ├─ 调用 Service，将结果映射为 Responses 模型
   └─ 不写业务规则，不接触 ISqlSugarClient 与 Entities
   │
   ▼
Service（Services/，按模块拆分）
   ├─ 业务规则：唯一性冲突转错误码、状态机流转校验、md5 计算、未发布变更判断
   ├─ 事务编排：发布/回滚经 Repository 层的 DatabaseTransactionRunner 执行，不直接开事务
   └─ 只操作 Models/Domain 业务数据类，通过 Repository 读写数据库
   │
   ▼
Repository（Repositories/，按模块拆分）
   ├─ 唯一接触 Entities 与 ISqlSugarClient 的层：Queryable / Insertable / Updateable / 原生 SQL 收口于此
   ├─ 实体 ↔ 业务数据映射（静态 From/To 方法）
   └─ 对外只出入 Models/Domain 业务数据类
   │
   ▼
SqlSugar（ISqlSugarClient，单例 SqlSugarScope）
   └─ 实体映射与 SQL 生成，访问 PostgreSQL
```

职责边界约定：

- Controller 薄：只做「接参 → 调 Service → 返回统一响应」，异常交给全局异常处理中间件转统一错误响应；
- Service 是唯一的业务规则承载层，且按模块严格拆分（namespace 的只管 namespace，environment 的只管 environment）；跨模块需求（如级联拒绝删除需要查看下级资源）通过注入对方模块的 Repository 只读完成，不把别的模块逻辑写进本模块；
- Repository 是唯一的数据访问层，同样按模块划分；ISqlSugarClient 只允许注入到 Repository，Service 一律不直接接触；事务由 Repository 层提供的 DatabaseTransactionRunner 统一入口，SqlSugarScope 单例保证事务内各 Repository 操作参与同一环境事务；
- 实体（Entities）不出业务层：Repository 对外出入 Models/Domain 业务数据类（record），Service / Controller / Requests / Responses 一律不得引用 Entities，对外一律转为 Responses 模型；SqlSugarSetup 作为数据访问基础设施，允许引用实体注册软删除全局过滤器；
- 不额外抽 `IXxxRepository` 仓储接口，直接以类注册 DI（单一实现场景接口只增加文件数），避免过度分层。

## 5. SqlSugar 接入方案

> 本章内容自 `../设计文档/配置中心设计文档.md` 迁入，设计文档中不再保留实现映射细节。

### 5.1 命名映射策略（二选一）

本方案采用 **方式 A：属性 PascalCase + `ColumnName` 显式映射 snake_case**，映射关系一目了然、不依赖全局约定，第 6 章实体示例均按此编写。

另一种可选方式 B 是全局 `EntityService` 自动转换（实体上无需逐列写 ColumnName）：

```csharp
var db = new SqlSugarClient(config, client =>
{
    client.CurrentConnectionConfig.ConfigureExternalServices = new ConfigureExternalServices
    {
        EntityService = (property, column) =>
        {
            // PascalCase -> snake_case，如 ConfigurationKey -> configuration_key
            column.DbColumnName = UtilMethods.ToUnderLine(column.DbColumnName);
        }
    };
});
```

### 5.2 类型选型建议

- **TIMESTAMPTZ**：建议实体使用 `DateTimeOffset` / `DateTimeOffset?`，与"含时区时间戳"语义精确对应（Npgsql 原生支持）。若团队习惯 `DateTime`，需保证全链路统一使用 UTC（Npgsql 6+ 要求 timestamptz 写入 `DateTimeKind.Utc`），否则易踩时区坑。**推荐 DateTimeOffset**。
- **JSONB**（`config_center_operation_log.detail`）：
  - 若属性为强类型对象/字典：`[SugarColumn(ColumnName = "detail", IsJson = true, ColumnDataType = "jsonb", IsNullable = true)]`，SqlSugar 自动序列化/反序列化；
  - 若属性为 `string`（存原始 JSON 文本）：只需 `ColumnDataType = "jsonb"`，不加 `IsJson`。
  - 实体示例采用 `string` + `ColumnDataType = "jsonb"`，最简单直观。
- **SMALLINT** → `short`；**BIGINT** → `long`；**CHAR(32)/VARCHAR/TEXT** → `string`。
- 主键均为数据库 IDENTITY 自增：`[SugarColumn(IsPrimaryKey = true, IsIdentity = true)]`，插入时无需赋值（表为 `GENERATED ALWAYS AS IDENTITY`，显式插入 id 会报错，`IsIdentity = true` 可保证 SqlSugar 生成的 INSERT 不包含 id 列）。
- **updated_at 由数据库触发器维护**：建表脚本为含 `updated_at` 的表创建了 `BEFORE UPDATE` 触发器（通用函数 `function_automatic_update_updated_at()`），行更新时自动刷新；应用层无需手动赋值，SqlSugar 更新时不必 set `UpdatedAt`（建议用 `UpdateColumns` 指定业务列，不包含 updated_at，交由触发器处理）。

### 5.3 PostgreSQL 连接配置

```csharp
// Program.cs 中注册（NuGet：SqlSugarCore）
builder.Services.AddSingleton<ISqlSugarClient>(sp =>
{
    var db = new SqlSugarScope(new ConnectionConfig
    {
        DbType = DbType.PostgreSQL,
        ConnectionString = builder.Configuration.GetConnectionString("PostgreSQL"),
        IsAutoCloseConnection = true,
        InitKeyType = InitKeyType.Attribute   // 按实体特性解析主键/自增
    });
    return db;
});
```

```json

  }

```

### 5.4 落地方式：SQL 脚本 vs CodeFirst

| 方式 | 做法 | 评价 |
|------|------|------|
| **手工执行 SQL（推荐）** | psql 执行 `配置中心建表脚本.sql`，实体只做映射（DbFirst 思路） | 部分唯一索引（`WHERE deleted_at IS NULL`）、延迟外键、CHECK 约束、COMMENT 等 PostgreSQL 特性完整可控；DDL 进入版本管理，可审查、可回放 |
| CodeFirst | `db.CodeFirst.InitTables(typeof(ConfigCenterConfiguration), ...)` | 适合快速原型；但 SqlSugar CodeFirst 无法表达部分唯一索引、CHECK 约束、循环外键延迟建立等本设计的关键约束，生成结果与设计脚本会有偏差 |

**结论：直接执行 SQL 脚本建库，禁用 CodeFirst 建表；实体类仅承担 ORM 映射职责。**

    public long? EnvironmentId { get; set; }

    [SugarColumn(ColumnName = "group_id", IsNullable = true)]
    public long? GroupId { get; set; }

    [SugarColumn(ColumnName = "configuration_id", IsNullable = true)]
    public long? ConfigurationId { get; set; }

    [SugarColumn(ColumnName = "operation", Length = 32)]
    public string Operation { get; set; } = string.Empty; // CREATE/UPDATE/PUBLISH/ROLLBACK/OFFLINE/DELETE

    // JSONB 列：属性为 string 时仅指定 ColumnDataType；
    // 若改为强类型对象/Dictionary，则加 IsJson = true 由 SqlSugar 自动序列化。
    [SugarColumn(ColumnName = "detail", ColumnDataType = "jsonb", IsNullable = true)]

## 7. API 设计

### 7.1 统一响应结构与错误码

所有接口返回统一包裹结构：

```json
{
  "code": 0,
  "message": "success",
  "data": { }
}
```

| 约定 | 说明 |
|------|------|
| code = 0 | 业务成功，`data` 为业务数据（对象 / 列表 / 分页结构） |
| code != 0 | 业务失败，`message` 为面向用户的错误描述，`data` 为 null |
| 分页结构 | `data: { items: [...], total: 100 }`，请求用 `pageIndex` / `pageSize` 查询参数 |
| HTTP 状态码 | 业务失败也返回 200（错误由 code 表达）；400 参数校验失败、404 路由不存在、500 未处理异常（由全局异常中间件转统一结构） |

错误码分段约定：

| 区间 | 含义 | 示例 |
|------|------|------|
| 0 | 成功 | — |
| 10000+ | 通用错误 | 10001 参数校验失败、10002 资源不存在 |
| 20000+ | 基础维度（命名空间/环境/配置组） | 20001 命名空间 key 已存在、20002 环境 key 在命名空间内已存在、20003 配置组 key 在环境内已存在、20004 存在未删除的下级资源，拒绝删除 |
| 30000+ | 配置与发布 | 30001 配置 key 在组内已存在、30002 无未发布变更（重复发布）、30003 目标回滚版本不存在、30004 发布并发冲突 |

业务异常（BusinessException）的 message 只包含对客户端安全且必要的业务说明，不含内部实现细节（异常堆栈、SQL 语句、连接信息等）；非业务异常的详情只记服务端日志，客户端统一收到 10000 服务器内部错误。

### 7.3 客户端接口（ClientConfigurationController，`/api/client`）

只返回 `status='PUBLISHED' AND deleted_at IS NULL` 的配置，内容取 `published_version_id` 指向的版本快照（保证读到已发布内容而非编辑中的草稿）：

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | /api/client/configurations?namespaceKey=&environmentKey=&groupKey= | 按组批量拉取已发布配置（key、content、format、md5、版本号） |
| GET | /api/client/configurations/{configurationKey}?namespaceKey=&environmentKey=&groupKey= | 拉取单个已发布配置 |
| GET | /api/client/notifications?namespaceKey=&environmentKey=&groupKey=&md5= | 长轮询变更探测：携带客户端本地 md5，服务端对比生效版本 md5，不一致立即返回变更标记；一致则挂起（默认 30~60 秒）直到变更或超时返回未变更 |

长轮询实现要点：

- 挂起基于 `CancellationToken` + 超时任务实现，避免阻塞线程池线程；
- 阶段一实现可用「挂起期间周期性对比 md5」的简单轮询式实现；阶段二引入 ReleaseMessage 机制后改为发布事件唤醒（参见 `./项目整体架构设计.md` 演进路线）；
- 客户端标识 key 使用业务 key（namespaceKey / environmentKey / groupKey）而非数据库 ID，客户端无需感知内部主键。

## 8. 核心流程实现设计

> 机制层面的定义（版本语义、状态机、判定规则）见 `../设计文档/配置中心设计文档.md` 第 4、5 章，本章落到服务层实现视角。

### 8.1 编辑保存与 md5（ConfigurationService）

- 新建：写入 `config_center_configuration`，`status='DRAFT'`，`latest_version_number=0`，服务端以配置内容计算 32 位小写 MD5 写入 `md5` 列（md5 一律由服务端计算，不信任前端传值）；
- 保存编辑：只更新当前态字段 `content / format / md5 / description / tags / updated_by`（`updated_at` 由数据库触发器自动刷新，无需赋值），**不产生版本记录**、不改变 status；
- 「有未发布变更」判定：当前 `md5` ≠ `published_version_id` 指向版本的 `md5`（或从未发布）；列表接口将该布尔标记算好返回，前端不做 md5 对比。

### 8.2 发布事务（PublishService）

事务内顺序执行：

1. 读取配置行并校验（存在、未软删除；可选校验「无未发布变更」时拒绝重复发布）；
2. `latest_version_number = latest_version_number + 1`（原子自增，见第 9 章）；
3. 将当前 `content / format / md5` 写入 `config_center_configuration_version`（`version_number = 新版本号`，`change_type='CREATE'`（首发）或 `'UPDATE'`，带变更备注）；
4. 更新 `config_center_configuration`：`published_version_id = 新快照 id`、`status='PUBLISHED'`、`published_at=now()`；
5. 写 `config_center_operation_log`（operation='PUBLISH'，detail 记录版本号与备注）。

任一步失败整体回滚，保证「版本号、快照、指针、日志」四者一致。

### 8.3 回滚（PublishService）

回滚**不回退版本号**，而是以历史版本内容生成一个新版本，保持版本线性递增、历史可追溯。事务内：

1. 取目标历史版本 `config_center_configuration_version(version_number=N)` 的 content / format / md5，不存在则报错（30003）；
2. `latest_version_number + 1`，写入新快照，`change_type='ROLLBACK'`，备注中记录"回滚自 vN"；
3. 更新 `config_center_configuration` 当前态内容（content / format / md5 同步为该历史版本值）与 `published_version_id`，`status='PUBLISHED'`、`published_at=now()`；
4. 写操作日志（operation='ROLLBACK'）。

### 8.4 软删除（全资源统一策略）

软删除不仅适用于配置项，而是 **namespace / environment / group / configuration 四类主资源的统一删除策略**，全系统禁止物理删除：

- **删除即置 `deleted_at = now()`**，其他字段（含 status）不变；版本与审计日志保留可审计（config_center_configuration_version 与 config_center_operation_log 不提供删除能力，不设 deleted_at）；
- **级联语义：存在未删除子资源时拒绝删除**。删除 namespace 前检查其下是否存在 `deleted_at IS NULL` 的环境，删除 environment 前检查未删除的配置组，删除 group 前检查未删除的配置项；命中则拒绝并返回业务错误码 20004（按 7.1 约定 HTTP 仍返 200，错误由 code 表达，语义等价于 HTTP 409）。不采用级联软删除，避免一次误操作静默删掉整棵子树，用户需自底向上逐层清空后再删除父资源，更安全且意图明确；
- **部分唯一索引自动放行同 key 重建**：`unique_namespace_key`、`unique_environment_namespace_key`、`unique_group_environment_key`、`unique_configuration_key` 均为 `WHERE deleted_at IS NULL` 的部分唯一索引，软删除后同 key 可立即重建；
- **查询约定**：所有列表/详情查询（管理端与客户端）默认过滤 `deleted_at IS NULL`，用 SqlSugar 全局查询过滤器（QueryFilter）统一实现，避免逐处手写 Where 条件遗漏：

```csharp
// SqlSugarSetup.cs：为含 DeletedAt 的实体统一注册软删除过滤器
db.QueryFilter.AddTableFilter<ConfigCenterNamespace>(it => it.DeletedAt == null);
db.QueryFilter.AddTableFilter<ConfigCenterEnvironment>(it => it.DeletedAt == null);
db.QueryFilter.AddTableFilter<ConfigCenterConfigurationGroup>(it => it.DeletedAt == null);
db.QueryFilter.AddTableFilter<ConfigCenterConfiguration>(it => it.DeletedAt == null);
// 少数需要读取已删除记录的场景（如审计回溯）用 ClearFilter 临时绕过
```

### 8.5 审计日志写入（Repositories/OperationLogRepository）

- 各业务 Service 在写操作（CREATE / UPDATE / PUBLISH / ROLLBACK / OFFLINE / DELETE）成功后调用 `OperationLogRepository.InsertAsync` 写 `config_center_operation_log`，不引入切面（AOP），日志写入点与业务逻辑同处一个方法，链路直观、代码最少；
- detail（JSONB）记录请求参数等关键信息；operator 取请求头约定值 `X-Operator`（阶段一无用户体系，缺省 system）；client_ip_address 取 `HttpContext.Connection.RemoteIpAddress`（有反向代理时可演进为优先 X-Forwarded-For）；操作人 / IP 的提取由 Service 经 `OperationHelper` 完成后以字符串传入 Repository，HttpRequest 不进入数据访问层；
- 发布 / 回滚这类事务型操作的日志在 PublishService 编排的事务内写入（保证与业务变更同生共死）。

## 9. 事务与并发考虑

- **发布并发时 latest_version_number 的原子递增**：并发发布同一配置时，若「先读后写」会产生相同版本号。用数据库侧原子自增避免竞态：

```sql
UPDATE config_center_configuration
SET latest_version_number = latest_version_number + 1
WHERE id = @id AND deleted_at IS NULL
RETURNING latest_version_number;
```

  事务内先执行该语句拿到新版本号，再写快照与指针，两个并发事务会在行锁上串行化，各自拿到不同版本号；

- **唯一约束兜底**：即使应用层出现漏洞，`UNIQUE(configuration_id, version_number)` 也会让重复版本号的第二个事务失败回滚，不会产生脏数据；捕获该唯一冲突后转为业务错误 30004（发布并发冲突），提示用户重试；
- **创建类接口的唯一冲突**：命名空间 / 环境 / 配置组 / 配置项的创建同样依赖数据库唯一约束兜底，四者均为 `WHERE deleted_at IS NULL` 的部分唯一索引（`unique_namespace_key`、`unique_environment_namespace_key`、`unique_group_environment_key`、`unique_configuration_key`），仅约束未软删除记录，软删除后同 key 可重建；应用层先查后插仅用于给出友好提示；
- **事务边界**：Repository 层提供统一事务入口 `DatabaseTransactionRunner`（内部封装 `db.Ado.UseTranAsync`），发布 / 回滚由 PublishService 经该入口编排全流程；Service 不直接接触 ISqlSugarClient，Controller 层不开事务。
